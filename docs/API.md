# llmhost API — контракт для внешних клиентов

Для программ llmhost выглядит как обычный сервер с API в формате OpenAI.
Управление моделями вынесено в отдельный control API. Между клиентом и
движком расположен тонкий слой llmhost. Он сохраняет неизменными порты,
ключ, выбор модели и форму ошибок. Клиенты не зависят от версии движка:
при обновлении llama.cpp изменяется реализация, а не контракт.

Два порта (оба по умолчанию слушают только `127.0.0.1`):

| Порт | Что это | Для кого |
|------|---------|----------|
| `7330` | OpenAI-совместимый API (`/v1/...`) | чаты, IDE-плагины, скрипты, любые OpenAI-SDK |
| `7331` | Control API (`/v0/...`) | загрузка и выгрузка моделей, статус, каталог Hugging Face |

Порты меняются в настройках (`llmhost.conf`: `openai-port`,
`control-port`); во всех примерах ниже — значения по умолчанию.

---

## 1. Быстрый старт

```python
# pip install openai
from openai import OpenAI

client = OpenAI(
    base_url="http://127.0.0.1:7330/v1",
    api_key=open("data/token.txt").read().strip(),
)

r = client.chat.completions.create(
    model="Qwen3-30B-A3B-Instruct-2507-Q4_K_M",   # или "any"
    messages=[{"role": "user", "content": "Привет!"}],
)
print(r.choices[0].message.content)
```

```javascript
// npm i openai
import OpenAI from "openai";
const client = new OpenAI({
  baseURL: "http://127.0.0.1:7330/v1",
  apiKey: require("fs").readFileSync("data/token.txt", "utf8").trim(),
});
const r = await client.chat.completions.create({
  model: "any",
  messages: [{ role: "user", content: "Привет!" }],
});
```

```bash
TOKEN=$(cat data/token.txt)
curl -s http://127.0.0.1:7330/v1/chat/completions \
     -H "Authorization: Bearer $TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"model":"any","messages":[{"role":"user","content":"Привет!"}]}'
```

Разделение операций: генерация текста обслуживается портом 7330. Все
остальные операции (выбор модели для загрузки, сведения о свободной
памяти, скачивание моделей) обслуживаются портом 7331.

## 2. Аутентификация

- Все запросы, кроме `GET /health` и preflight-запросов браузера
  (OPTIONS), требуют заголовок:

  ```
  Authorization: Bearer <содержимое token.txt из каталога данных>
  ```

- Токен создаётся при первом запуске llmhost: 64 символа, файл
  `token.txt` в каталоге данных с правами 600. Тот же токен возвращает
  `GET http://127.0.0.1:7331/v0/credentials`.
- Доступ можно выдать и поимённо: команды `lhctl tokens` создают
  отдельные токены для `/v1` (чтобы не передавать главный ключ). Пока
  существует хотя бы один именованный токен, анонимный доступ закрыт.
- Аутентификацию можно выключить (`openai-auth: false` в
  конфигурационном файле) — не рекомендуется: порт слушает localhost,
  но любой локальный процесс и любая вкладка браузера (см. §3) смогут
  пользоваться вашими моделями.
- Неверный токен → `401` с телом-конвертом (см. §5). Если токен не
  удалось создать (генератор случайных чисел или файл недоступны) —
  API отвечает `503` «закрыт» и не обслуживает анонимные запросы.

## 3. CORS (браузерные клиенты)

CORS обрабатывает сам llmhost, и поведение не зависит от версии движка:

- На preflight (`OPTIONS` с заголовком `Origin`) llmhost отвечает сам,
  статусом `204`, без проверки токена — браузер авторизацию на preflight
  не передаёт. Возвращаются `Access-Control-Allow-Methods` и
  `Access-Control-Allow-Headers` (эхо запрошенных).
- Заголовок `Access-Control-Allow-Origin: <Origin>` с `Vary: Origin`
  ставится **только доверенным источникам**: `http(s)://localhost[:порт]`
  и `http(s)://127.0.0.1[:порт]` — всегда, плюс явный список
  `cors-origins` из llmhost.conf (через запятую). Посторонний сайт эти
  заголовки не получает и прочитать ответ локального API не может.
  Cookies не нужны — клиент сам подставляет
  `Authorization: Bearer …`, поэтому `credentials: "include"` не требуется.
- Preflight от недоверенного источника получает `204` без CORS-заголовков
  — браузер считает вызов запрещённым.
- Без заголовка `Origin` CORS-заголовки не ставятся вовсе: клиентам без
  браузера они не нужны.

Веб-приложение с `localhost:3000` обращается к
`http://127.0.0.1:7330/v1` напрямую; страница из интернета сделать
этого не может. Внешний фронтенд добавляется в `cors-origins`.

## 4. Порт 7330 — OpenAI-совместимый API

### 4.1 Выбор модели

Поле `model` в запросе — **идентификатор модели**: имя `.gguf`-файла без
расширения (например, `Qwen3-30B-A3B-Instruct-2507-Q4_K_M`). Полный
список идентификаторов — `GET /v1/models`.

| Что клиент прислал | Что произойдёт |
|---|---|
| id модели, уже находящейся в видеопамяти | запрос обслуживается этой моделью |
| id модели, которая есть в реестре, но не в видеопамяти | **модель загрузится в видеопамять автоматически** (первый запрос дождётся загрузки: для небольшой модели — секунды, для крупной — минуты) |
| `any` или поле `model` отсутствует | отвечает модель по умолчанию: последняя использованная или единственная подходящая; работает и сразу после старта сервера |
| неизвестный id | `400` с пояснением и указанием проверить `GET /v1/models` |
| модель для векторных представлений (например, `nomic-embed-text-v1.5.Q8_0`) в `/v1/embeddings` | авто-загрузка и ответ; основной моделью чата такая модель быть не может — она не генерирует текст |
| запрос без `model`, когда модели для выбора нет | `400` «модель не выбрана…» — неявная подстановка другой модели недопустима |

Правила действуют для `/v1/chat/completions` и `/v1/completions`;
подстановка модели по умолчанию — только для этих «разговорных»
запросов. Для `/v1/embeddings` модель указывается явно.

### 4.2 `GET /v1/models`

OpenAI-формат:

```json
{"object": "list", "data": [{"id": "Qwen3-30B-A3B-Instruct-2507-Q4_K_M",
  "object": "model", "owned_by": "llamacpp", "created": 1759...}, ...]}
```

В списке — все модели реестра (файлы в каталоге моделей), включая те,
что сейчас не в видеопамяти: обращение к модели вызовет её загрузку
(§4.1).

### 4.3 `POST /v1/chat/completions`

Обязательное поле — `messages` (формат OpenAI: `role` равен
`system`/`user`/`assistant`; `content` — строка или массив частей
`[{"type":"text","text":"…"}]`).

Поддерживаются и передаются движку как есть: `model`, `max_tokens`,
`temperature`, `top_p`, `top_k`, `stop` (строка или массив), `seed`,
`stream`, `stream_options.include_usage`, `presence_penalty`,
`frequency_penalty`, `repeat_penalty`, JSON-схемы (`response_format`) и
прочие параметры llama.cpp. Всё, что понимает llama.cpp вашей версии,
передаётся движку без изменений; здесь задокументировано только то, что
llmhost гарантирует сам, независимо от версии движка.

Гарантии llmhost:

- Обычный (не потоковый) ответ: `200`, тело
  `{"id","object":"chat.completion","created","model","choices":[
  {"index","message":{"role":"assistant","content"},"finish_reason"}],
  "usage":{...}}`.
- `finish_reason`: `"stop"` — естественное окончание или сработавшая
  stop-строка; `"length"` — достигнут лимит `max_tokens`.
- Потоковая выдача (`stream: true`): `Content-Type:
  text/event-stream`, события `data: {...}` с `object:
  "chat.completion.chunk"`, первый чанк несёт `delta.role = "assistant"`,
  финал — `data: [DONE]`. С `stream_options: {"include_usage": true}`
  предпоследний чанк содержит `usage` (без `choices`).
- `max_tokens: 1` — ровно один токен и `finish_reason: "length"`;
  `max_tokens: 0` — `400`.
- Юникод (кириллица, эмодзи) проходит в обе стороны без искажений.
- Обрыв соединения посреди генерации: генерация останавливается, сервер
  продолжает обслуживать следующие запросы.

Пример потоковой выдачи утилитой curl:

```bash
curl -N http://127.0.0.1:7330/v1/chat/completions \
     -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
     -d '{"model":"any","stream":true,"max_tokens":64,
          "messages":[{"role":"user","content":"Стихотворение про горы"}]}'
```

### 4.4 `POST /v1/completions` (устаревший формат)

```json
{"model": "Qwen3-30B-A3B-Instruct-2507-Q4_K_M",
 "prompt": "Скажи одно слово: привет", "max_tokens": 16}
```

Ответ — `{"id","object":"text_completion","choices":[{"text":"…",
"finish_reason":…}],"usage":…}`. Поле `prompt` — строка (массив строк —
как понимает движок).

### 4.5 `POST /v1/embeddings`

```json
{"model": "nomic-embed-text-v1.5.Q8_0", "input": "привет, мир"}
```

- Ответ: `{"object":"list","data":[{"object":"embedding","index":0,
  "embedding":[0.012, …]}],"usage":…}` — размерность вектора своя у
  каждой модели (у nomic-embed-text — 768).
- `input` — строка или массив строк.
- Обращение к модели для векторов **загружает её в видеопамять
  автоматически**; по простою она выгружается, как и любая другая.
- Запрос вектора у разговорной модели → `501` с объяснением: это
  ограничение самой модели, а не ошибка клиента.

### 4.6 Прочее (прозрачная пересылка)

`GET /health` (публичный, без токена — признак работоспособности
сервера), `POST /tokenize`, `POST /detokenize`, `POST /apply-template`,
`/v1/responses`, `/v1/messages` (формат Anthropic), `/v1/rerank`,
`/slots`, `/props` — пересылаются движку без изменений. Их наличие
зависит от версии llama.cpp: **в свой контракт llmhost их не включает** и
при смене движка не гарантирует.

## 5. Ошибки — стабильный конверт

Любая ошибка от llmhost (и от движка сквозь него) выглядит одинаково:

```json
{"error": {"message": "человекочитаемое объяснение",
           "type": "invalid_request_error",
           "code": 400}}
```

- `code` всегда равен HTTP-статусу ответа.
- `type` — словарь OpenAI: `invalid_request_error` (ошибка клиента),
  `authentication_error` (401), `not_found_error` (404), `api_error`
  (проблема на стороне сервера).
- `message` достаточно, чтобы понять и исправить запрос без обращения
  к журналам.

Нормализация: llama.cpp часть ошибок разбора запроса (некорректный
JSON, «нет role у сообщения») возвращает как `500 server_error`.
llmhost переводит их в `400 invalid_request_error` — ошибка клиента не
должна выглядеть как отказ сервера. Настоящие отказы движка остаются
5xx.

**Проверка запроса до запуска моделей.** Обязательные поля проверяются
до обращения к движку — некорректный запрос не вызывает загрузку моделей
в видеопамять и не может блокироваться в ожидании ответа:
`/v1/chat/completions` требует непустой массив `messages` (каждый
элемент — объект с непустой строкой `role`; `content`, если есть, —
строка, массив частей или null), `/v1/completions` — `prompt` (строка
или массив строк/чисел-токенов), `/v1/embeddings` — `input`.
Необязательные поля с известными именами (`model`, `stream`,
`temperature`, `top_p`, `max_tokens`, `n`, `seed`, штрафы) при наличии
проверяются на тип. Незнакомые поля передаются движку без изменений.
Тело больше 256 МБ — `413` (длинные промпты и вложения).

Типовые коды:

| Код | Когда |
|-----|-------|
| 400 | некорректный JSON; пустой или неверный `messages`; нет `prompt`/`input`; неверный тип известного поля; `max_tokens: 0`; модель не указана, а моделей для выбора нет |
| 401 | нет или неверен Bearer-токен |
| 404 | неизвестный id модели |
| 413 | тело запроса больше 256 МБ |
| 501 | модель не умеет запрошенное (вектор у разговорной модели) |
| 502 | движок не отвечает (например, ещё запускается) |
| 503 | модель загружается либо загрузка не удалась — повторите запрос; в режиме harness — память занята при выключенной очереди (`queue-ttl = 0`) |
| 504 | в режиме harness — истёк срок ожидания в очереди пробуждения (`queue-ttl`), в сообщении указывается занятая модель; иначе — движок не вернул заголовки за 300 с |

## 6. Порт 7331 — Control API

Тот же Bearer-токен, тот же конверт ошибок. Все ответы — JSON
(`application/json`).

### Статус и оборудование

- `GET /v0/status` — сводка: версия llmhost, агрегатное состояние
  (`asleep`/`loading`/`loaded`), какая модель в видеопамяти, данные
  карт (имя, свободно/всего), лимиты. `harness_mode` всегда `true`
  (демон сам решает, что, куда и когда загружать): у каждой модели в
  `models` — её `port` и `pid`, `queue_depth` — число запросов,
  ожидающих в очереди пробуждения, `models_max` — лимит резидентов,
  `busy` — идёт ли генерация прямо сейчас.
- `GET /v0/hardware` — только данные карт.

### Модели

- `GET /v0/models` — реестр: `id`, путь к файлу, архитектура, квант,
  размер, состояние (`unloaded`/`loading`/`loaded`), признак
  векторной модели, индикатор `fit` (поместится ли модель в видеопамять
  и какой максимальный контекст).

  ```json
  {"models": [{"id": "Qwen3-30B-A3B-Instruct-2507-Q4_K_M",
               "state": "loaded", "embedding": false, "fit": {...}}, ...]}
  ```

- `DELETE /v0/models` — удалить файл модели с диска **безвозвратно**
  (корзина не используется). Тело: `{"path": "…"}` или
  `{"name": "…"}`. Модель, находящаяся в видеопамяти, сначала выгружается;
  группа частей `…-00001-of-…` удаляется целиком, вместе со спутниками
  репозитория (vision-проекция, MTP-модуль). Ответ
  `200 {"deleted":"<путь>","recycle":false}`; нет файла или имени →
  `404`, пустое тело → `400`.

- `POST /v0/load` — загрузить модель в видеопамять. Тело:
  `{"name": "<id или имя файла>"}` или `{"path": "<путь к .gguf>"}`.
  Ответ `202 {"state":"loading","model":"<id>"}`; повторный вызов для
  уже загруженной модели также возвращает `202`. Ошибки: `404` —
  модели нет в реестре или файла нет по указанному пути (проверяется
  сразу — загрузка по отсутствующему пути не запускается); `409` —
  загрузка той же модели уже идёт.
- `POST /v0/unload` — выгрузить из видеопамяти: `{}` (все модели) или
  `{"model": "<id>"}` (одну). Неизвестный id → `404`; запрос для
  незагруженной модели завершается успешно. **Модель, обслуживающая
  запросы прямо сейчас, не выгружается никогда**: конкретная занятая →
  `409` с объяснением; при выгрузке «всей» занятые остаются в памяти и
  перечисляются в ответе полем `busy_kept` — их выгрузит сторож простоя.
  Явное исключение — `{"model": "<id>", "force": true}`: модель
  останавливается принудительно, все её текущие генерации обрываются
  для всех клиентов. `"force"` без `"model"` отклоняется → `400`
  (принудительной выгрузки «всех» нет); не-булево значение `"force"`
  → `400`.

### Метрики (Prometheus)

- `GET /v0/metrics` — текст формата Prometheus
  (`text/plain; version=0.0.4`), под тем же Bearer-токеном (в
  scrape-конфиге — `bearer_token`). Серии:
  `llmhost_requests_total{model,endpoint}`,
  `llmhost_errors_total{model,kind}` (kind: upstream_error / unreachable /
  client_gone / auth / bad_request / unavailable / queue_timeout /
  not_found), `llmhost_prompt_tokens_total` /
  `llmhost_completion_tokens_total{model}` (из usage ответов),
  `llmhost_response_bytes_total{model,endpoint}`,
  `llmhost_request_seconds_sum/_count{model,endpoint}` (среднее —
  отношением скоростей роста), `llmhost_generation_tps{model}` (сглаженная
  скорость генерации), `llmhost_vram_bytes{card,name,kind=free|total}`,
  `llmhost_model_state{model,state}`, `llmhost_supervisor_state{state}`,
  `llmhost_up`. В режиме harness добавляются серии очереди пробуждения:
  `llmhost_queue_depth{model}` (сколько ждёт сейчас),
  `llmhost_queue_wait_ms_sum/_count{model}` (сколько в среднем ждали),
  `llmhost_queue_timeouts_total{model}` (истечение срока ожидания).
  Счётчики хранятся в памяти демона — рестарт обнуляет их (для Prometheus
  это штатный сброс счётчика). Источник данных — сам прокси: каждый
  запрос и его usage уже проходят через него, агрегатор ничего не
  опрашивает. Поверх счётчиков прокси демоном опрашиваются `/metrics`
  живых детей — точная телеметрия движка по-модельно: серии
  `llmhost_engine_decode_tps{model}` / `llmhost_engine_prompt_tps{model}`
  (средние скорости декода и префилла),
  `llmhost_engine_decode_tokens_total` / `llmhost_engine_decode_seconds_total`
  (мгновенная скорость — отношением скоростей роста),
  `llmhost_engine_prompt_tokens_total` (без кэшированных),
  `llmhost_engine_spec_accepted_total` / `llmhost_engine_spec_draft_total`
  (приём спекуляции). Тот же текст по-человечески — `lhctl metrics [-w сек]`
  и экран метрик TUI (клавиша `m`).

### Per-model переопределения

- `POST /v0/models/ctx` — ручной контекст модели:
  `{"name"|"path", "ctx": N}`; `{"ctx": 0}` — снять пин. Читается
  поле `ctx_override` в `GET /v0/models`.
- `POST /v0/models/cache` — размер кэша MoE модели в МиБ:
  `{"name"|"path", "mib": N}`; `0` — решает `[general]`. Применяется при
  следующей загрузке модели.
- `POST /v0/models/mtp` — MTP-спекуляция модели:
  `{"name"|"path", "mode": "auto"|"on"|"off"}`.
- `POST /v0/models/vision` — vision-режим модели:
  `{"name"|"path", "mode": "auto"|"off"}`.
- `POST /v0/models/thinking` — thinking-режим модели:
  `{"name"|"path", "mode": "auto"|"on"|"off"}` (auto — движок детектит
  по шаблону, on/off — форс `--reasoning`). Переключение усыпляет слот —
  первый запрос поднимет ребёнка с новым режимом. Те же ключи доступны
  как per-model секции llmhost.conf и командами `lhctl ctx/cache/mtp/
  vision/thinking`; режим и подсказки — в карточке TUI.

### Движок, скачивание, каталог, замер

- `GET /v0/engine` — сборки llama.cpp из `manifest.json` (какая
  зафиксирована, размер, установлена), зафиксированный релиз (`release`),
  активная сборка (`active`) и ход установки (`state/done/total/speed`).
  Зафиксированная версия — намерение; фактическая возвращается рядом:
  `installed_release` — релиз, который вернул установленный бинарник
  (`llama-server --version`), `mismatch: true` — если намерение
  и факт расходятся. То же расхождение пишется в журнал на старте и
  подсвечивается в `lhctl engine status`.
  `POST /v0/engine` `{"build":"vulkan"|"cuda12"}` — установить
  (`202`; загрузка идёт в фоне, прогресс — в `GET /v0/engine`; модели
  должны быть выгружены из видеопамяти, иначе `409`). Перед заменой
  бинарник проверяется: он обязан сообщить тот же релиз, что
  зафиксирован, — сборка с иным релизом установку не проходит.
- `POST /v0/engine/pin` — обновить зафиксированный релиз llama.cpp:
  `{"release":"latest"}` или `{"release":"b11379"}`. «latest» —
  новейший тег вида `bNNNNN` (версионные релизы `v*` — указатели без
  бинарников, они игнорируются). Контрольные суммы SHA256 и размеры
  берутся из GitHub API, сами архивы при этом не скачиваются; прежний
  манифест сохраняется в `manifest.json.bak`. Синхронный ответ
  `{"release","files","path"}`; бинарники не изменяются — установка
  после смены зафиксированной версии делается отдельным
  `POST /v0/engine`. Ошибки: `502` — нет архива с ожидаемым именем
  (схема имён в репозитории llama.cpp изменилась — зафиксируйте релиз
  вручную) или GitHub API недоступен; `409` — установка уже идёт.
- `GET /v0/pull` — статус скачивания: `state` — `idle | resolving |
  downloading | done | error | stopped`, прогресс — `done/total/speed`;
  `stopping: true` означает, что остановка запрошена, но ещё не дошла
  до конца. `POST /v0/pull`
  `{"repo":"org/repo","file":"model.gguf"}` — скачать модель с
  Hugging Face (без `file` — все `.gguf` репозитория; для закрытых
  репозиториев — переменная окружения `HF_TOKEN`). Вместо `org/repo`
  можно передать **короткое имя** (`"repo":"qwen3"`) — репозиторий и
  квант под ваши карты выберет llmhost (список — `GET /v0/aliases`; у
  vision-семейств проекция для картинок скачивается вместе с моделью).
  Неверное имя — ошибка `400`; если скачивание уже идёт — `409`.
  `DELETE /v0/pull` — остановить идущее скачивание (тот же механизм,
  что `lhctl pull stop` и `Ctrl-X` интерфейса): загрузка прерывается и
  доезжает до состояния `stopped`, недокачанный `.part` остаётся на
  диске — повторный `POST` с тем же репозиторием продолжает с места
  останова. Если скачивание не идёт — `400`.
- `GET /v0/aliases` — короткие имена для скачивания:
  `{"aliases":[{"name":"qwen3","repo":"unsloth/Qwen3-8B-GGUF","note":"…"}]}`.
  Список курируемый, стабильный между минорными версиями.
- `GET /v0/catalog/search?q=qwen&limit=24` — поиск по Hugging Face;
  параметр `limit` принимает значения от 1 до 100, некорректные
  заменяются значением по умолчанию.
- `GET /v0/catalog/model?repo=org/repo` — карточка репозитория (файлы,
  размеры; параметр `repo` обязателен, иначе `400`).
- `GET /v0/bench` — результат замера; `POST /v0/bench {"path":"<.gguf>"}`
  — измерить скорость модели (202; результат — в `GET /v0/bench`).

### Служебные

- `GET /v0/credentials` — `{"openai_base_url":"http://127.0.0.1:7330/v1",
  "openai_port":7330, "api_key":"…","auth_required":true}` — упрощает
  генерацию конфигурации клиента. `openai_base_url` — адрес с точки
  зрения сервера; веб-дашборд строит базу чата от хоста адресной строки
  и `openai_port`, чтобы работать из браузера на другой машине.
- `POST /v0/quit` — корректное завершение llmhost.

## 7. Жизненный цикл моделей

- **Автоматическая загрузка**: запрос к модели, которой нет в
  видеопамяти (как и `POST /v0/load`), вызывает её загрузку; запросы
  ожидают окончания загрузки (до 5 минут).
- **Выгрузка по простою**: если модель не использовалась
  `unload_after_min` минут (по умолчанию 15), она покидает видеопамять;
  первый же запрос загрузит её автоматически. Посреди ответа модель не
  выгружается никогда — ни по простою, ни по команде.
- **Правило занятости.** Модель, обслуживающая запрос,
  не выгружается. Если новому запросу не хватает памяти, демон выгружает
  только свободные модели. Если память удерживают занятые модели, запрос
  помещается в очередь и ожидает не дольше `queue-ttl` секунд
  (по умолчанию 120). При истечении срока ожидания возвращается ошибка
  `504` с объяснением. Число запросов, которые могут ожидать одну
  модель, задаёт `queue-depth` (по умолчанию 16).
- **Лимит моделей в видеопамяти** (`models_max`, по умолчанию 2): при
  переполнении выгружается наименее недавно использовавшаяся.
- **Параллельные запросы к одной модели**: несколько одновременных
  запросов обслуживаются одним движком (непрерывная обработка пачек),
  контекст делится между ними поровну.

## 8. Гарантии совместимости

llmhost гарантирует внешним клиентам независимо от версии движка:

1. Порты и способ аутентификации (§2), поведение CORS (§3).
2. Формы ответов `/v1/models`, `/v1/chat/completions`, `/v1/completions`,
   `/v1/embeddings` (§4) — словарь OpenAI.
3. Конверт ошибок `{"error":{message,type,code}}` и предсказуемые коды (§5).
4. Семантику выбора модели: авто-загрузка, `any`/модель по умолчанию,
   `400` на неизвестную (§4.1).
5. Стабильность control API (§6): существующие поля не переименовываются,
   новые добавляются.

Не гарантируется: прозрачные пересылки к движку (§4.6), точные тексты
сообщений об ошибках (гарантируется наличие `message`), значения `id` в
ответах.

Проверка контракта на работающем экземпляре: `python tests/api_e2e.py` —
51 проверка против запущенного llmhost (генерация, потоковая выдача,
обрывы соединения, параллелизм); многопользовательский сценарий режима
harness — `python tests/harness_multiuser_e2e.py`.
