# llmhost против Ollama

Возможности сверены по исходникам Ollama, снимок мастера `42e911bc` от
2026-10-02, внутри llama.cpp b11232. Все утверждения настоящего документа
об Ollama проверены чтением исходного кода проекта, а не по памяти и не
по документации.

llmhost представлен в этом документе начиная с версии beta10 и движка
b11382; рабочий сервер тогда же был обновлён до b11429, и поздние замеры
выполнены уже на нём. Каждое измерение датировано и привязано к версии
движка. Между сеансами значения изменяются в пределах дрейфа, поэтому
сравнивать корректно только замеры, выполненные подряд в одном сеансе;
далее такие прогоны именуются «подряд».

## Матрица подряд: движок b11897, harness против Ollama 0.40.11 (2026-10-27)

Повторение матрицы 09.10 против обновлённой версии Ollama: системный
сервис Ollama обновлён с 0.20.5 до 0.40.11 (релиз 24.10, внутри —
свежий llama.cpp; логи раннера ссылаются на PR llama.cpp #25655;
стенд 09.10 использовал 0.35.1, спекулятивная генерация по-прежнему
отсутствует). Настройки сервиса указывают на общий каталог моделей
(`OLLAMA_MODELS=/data/models`): те же веса импортированы локально
через Modelfile `FROM`, скачивание не выполнялось. Обе стороны на
Blackwell: Ollama — `CUDA_VISIBLE_DEVICES=0` (в CUDA-порядке Blackwell —
устройство 0; Vulkan-бэкенд выключен, иначе обе карты видны вне
фильтра), сторона llmhost — `main-gpu = 1`. Контекст у обеих сторон
32768; у Ollama FA+q8_0 из переменных окружения, у llmhost — политика
(при пине выбрала f16). Методика прежняя, с двумя уточнениями:
`/completion` на прокси больше не поддерживается (allow-list `/v1*`) —
сторона llmhost работает через `/v1/completions` с нонс-хвостами,
симметрично стороне Ollama; у 0.40.11 появился лимит повтора токенов,
обрывающий продолжения с temperature 0. Сохранившиеся прогоны Ollama:
0.6B — 2 из 3, 12B — 1 из 3, остальные — 3 из 3; медианы вычислены по
сохранившимся. Прогоны — `scripts/bench_l14_*.json`, сводка —
`scripts/bench_matrix_2026-10-27.json`.

После бенчмарка импорты удалены (`ollama rm`): блобы освобождены
(−42 ГиБ, в хранилище остался только bge-m3), исходные .gguf не
изменены. Прямой загрузки .gguf по пути в 0.40.11 нет (`/api/generate`
с путём отвечает «invalid model name»), поэтому при следующем бенчмарке
модели возвращаются локальным импортом без сети — Modelfile
`FROM <наш .gguf>` ×4: `ollama create
bench-qwen3-0.6b / bench-gemma4-12b / bench-qwen3.8-27b / bench-gemma4-26b`
(~15 минут копирования).

| Модель | ген. harness (b11897) | ген. Ollama 0.40.11 | Итог против Ollama |
|---|---|---|---|
| Qwen3-0.6B Q8_0 (плотная, 0.6B) | 517,3 ток/с | 466,9 ток/с | **+11%** |
| gemma-4-12b UD-Q5_K_XL (плотная, 12B) | 105,7 ток/с | 58,5 ток/с | **+81%** |
| Qwen3.8-27B UD-Q4_K_XL (плотная, 27B) | 52,2 ток/с | 32,0 ток/с | **×1,63** |
| gemma-4-26B A4B Q4_K_M (MoE) | 151,2 ток/с | 118,2 ток/с | **+28%** |

- **Преимущество на всех четырёх моделях, но результат 26B снизился.**
  Ollama прибавила в генерации на всех моделях (0.6B 438→467, 27B
  29,7→32,0, 26B 108→118 ток/с), llmhost — существенно на 12B (75→106:
  шесть недель работы движка над спекуляцией). Результат 26B снизился
  с 196 до 151 — причина в плане размещения llmhost, а не в изменениях
  Ollama (см. ниже).
- **Бенчмарк выявил регрессию размещения в llmhost.** Выходной слой
  26B/27B перенесён на CPU («весь груз с ним не помещается»); у 26B это
  −23% генерации (151 против 196 в матрице 09.10; профиль тех же дней
  в авто-форме 65536/q8_0 с выходным на GPU давал 173–176), у 27B —
  ещё и медленная холодная загрузка (9,4 с против 5,2 в матрице).
  Разбор в тот же вечер снял первую гипотезу: **f16-политика не
  является причиной — демоцию вызвала финальная проверка выходного
  слоя по фактическому состоянию карты.** Оба плана приняты в моменты,
  когда на Blackwell ещё находилась модель Ollama: модель 12B Ollama
  загружалась в 19:57:11 и выгружалась только при подгрузке её 27B
  (19:58:48) — план llmhost для 27B (19:58:11) видел ~13 свободных
  ГиБ вместо 23,4; модель 27B Ollama оставалась до подгрузки её 26B
  (20:00:12) — план llmhost для 26B (19:59:56) видел ~5 ГиБ. Весь план
  считается по конвенции «пустая карта минус запас», но последний шаг —
  повторный `ngl_with_output` в sup_harness/sup_router — получает
  фактическое состояние карты (`tgt.card` из
  `gpu_target_for(..., live=true)`); запас до отказа там ≥ 2 ГиБ, и
  `ngl_with_output` выполняет жёсткую демоцию: лестница стартует с уже
  срезанным ngl, и слой не возвращается на GPU даже после освобождения
  карты. На пустой карте обе модели проходят с запасом — проверено
  рабочей арифметикой `fit::estimate` с реальными метаданными (27B:
  потребность 22,1 ГиБ при 23,4 свободных; 26B: 20,6). С q8_0 демоция
  была бы той же (21,1 и 20,1 ГиБ при тех же свободных) — «предпочесть
  сжатый кэш» эту регрессию не устраняет. Дочерние процессы поднялись
  без спилла (52 и 151 ток/с): ручная выгрузка модели Ollama успевала
  освободить карту между планом и фактической загрузкой весов и внесла
  вклад в холодные 9,4 с у 27B (доля конкуренции уточнена ниже).
  Исправление внесено пунктом в ROADMAP: проверку выходного вести в
  плановой конвенции (или амбициозной попыткой вместо жёсткой демоции).
  Отдельно на будущее остаётся вопрос к политике для действительно
  тесных карт: если при пине f16+выходной не помещаются по плановой
  оценке — предпочитать сжатый кэш и оставлять выходной на GPU;
  ручной `cache-type` сильнее автоматики и вопрос обходит. Процедурно:
  выгрузка модели Ollama (`keep_alive=0`) обязана завершиться до
  `/v0/load` llmhost — в раннере это `wait_vram_clean`, ручной прогон
  эту гонку проиграл.
- **По предзаполнению впереди в большинстве случаев Ollama**: короткое
  — на всех четырёх (0.6B 12356 против 11697; 12B 1551 против 1113;
  27B 538 против 382; 26B 1657 против 1086; в матрице 09.10 llmhost
  был впереди на трёх из четырёх), длинное — на трёх из четырёх.
  Преимущество llmhost сохранилось только на длинном предзаполнении
  0.6B (39718 против 36828). Часть потерь llmhost — тот же
  перенесённый на CPU выходной слой (он же считает логиты при
  префилле), часть — улучшения раннера Ollama.
- **Первый токен быстрее у llmhost на всех четырёх**: 0,05–0,88 с
  против 0,08–1,18.
- **Холодная загрузка быстрее у llmhost на трёх из четырёх**:
  6,4/9,4/7,4 с против 15,4/12,4/13,1. На 0.6B новый загрузчик Ollama
  оказался быстрее (1,5 против 2,2 с; в матрице 09.10 было 5,5 против
  1–2 с у llmhost).

## Матрица подряд: движок b11476, оба режима llmhost (2026-10-09)

Повторение вечерней матрицы от 6 октября после двух обновлений со
стороны llmhost: движок с b11429 на b11476 и новый режим harness.
Методика прежняя, модели те же четыре, обе стороны на Blackwell.
Ollama — та же версия 0.35.1, чтобы изменялась только сторона llmhost.

Сторона llmhost измерена в обоих режимах. «Роутер» — цепочка «прокси →
роутер → процесс модели». «Harness» — прокси непосредственно в процесс
модели. Ollama прогнана один раз: от правок llmhost её результаты не
зависели. Сводка — в `scripts/bench_matrix_2026-10-09.json`, построчные
прогоны — в `scripts/bench_l12_*.json`.

| Модель | ген. роутер | ген. harness | ген. Ollama | Итог против Ollama |
|---|---|---|---|---|
| Qwen3-0.6B Q8_0 (плотная, 0.6B) | 510,4 ток/с | 512,9 ток/с | 438,0 ток/с | **+17%** |
| gemma-4-12b UD-Q5_K_XL (плотная, 12B) | 73,7 ток/с | 75,2 ток/с | 54,0 ток/с | **+36–39%** |
| Qwen3.8-27B UD-Q4_K_XL (плотная, 27B) | 54,8 ток/с | 54,7 ток/с | 29,7 ток/с | **×1,84** |
| gemma-4-26B A4B Q4_K_M (MoE) | 196,9 ток/с | 196,0 ток/с | 108,2 ток/с | **×1,82** |

- **Harness равен роутеру на всех четырёх**, в пределах разброса приёма
  черновиков: оркестрация со стороны демона не отражается на скорости
  генерации.
- **Холодная загрузка быстрее у llmhost на всех четырёх:** 1,1–6,2 с
  против 5,5–26,6 с. У 12B у Ollama в этот раз получилось 26,6 с — это
  разброс самой Ollama: 6 октября было 7,9 с. У llmhost в оба дня
  стабильно 5–6 с.
- **Первый токен у llmhost или наравне** на всех четырёх: 0,09–1,39 с
  против 0,13–1,42 с. «Цена полного стека» из замеров 6 октября на
  этом стенде не повторилась.
- **Замер выявил и устранил две регрессии llmhost.** Первый прогон дня
  показал на 12B и 26B скорость без спекуляции. Структурная проверка
  пары «основная модель + черновик» появилась 7 октября в исправлении
  петли 502 и отвергала родные головы gemma. У MTP-головы собственная
  внутренняя ширина, проекция лежит внутри файла: 1024 против 3840 у
  основной модели; жёсткий отказ по ширине отключал спекуляцию.
  Исправлено выбором в два прохода: сначала берутся головы с шириной
  основной модели, несовпадающие — только если совпадающих нет;
  словарь обязателен всегда.
  Второй прогон показал на 0.6B минус 9% в harness. Лестница
  классического пути всегда начинала с KV q8_0; политика сжатия, как в
  пресете роутера, для мелкой модели выбирала f16. q8, который просто
  помещался, работал медленнее: 464,9 против 510,4 ток/с. Исправлено:
  если политика выбрала f16, первая попытка выполняется с несжатым
  кэшем. Все числа таблицы получены после обоих исправлений; сторона
  Ollama от них не зависела.

## Возможности: сверка по исходникам (2026-10-02)

| | llmhost (Linux) | Ollama, снимок `42e911bc` |
|---|---|---|
| Дистрибуция | архив 3,7 МБ, статические бинарники; движок скачивается по манифесту с проверкой SHA256 | установщик ~1,4 ГБ, движок внутри |
| Контекст по умолчанию | свой для каждой модели: максимум, который помещается в видеопамять с запасом 1,5 ГиБ и полным грузом (vision-проекция, черновик), не выше обученного в модели; уточняется накопленными замерами; окна внимания читаются из метаданных GGUF | один на всех: ступени от **суммарной** ёмкости всех карт — ≥47 ГиБ → 262144, ≥23 ГиБ → 32768, иначе 4096 (`server/routes.go:2221-2225`) |
| Память: «поместится ли» | расчёт + **самообучение**: после каждой загрузки фактический след модели в видеопамяти записывается в профиль; следующий расчёт точнее | статический оценщик по метаданным + собственные пороги (`server/sched.go:855-930`); измеренное не запоминается — каждая загрузка считается с нуля |
| Запас на карте | 1,5 ГиБ — строгая граница бюджета (начальные контексты соседних процессов, пики vision; встроенная «проба влезания» llama.cpp выключена) | свои пороги внутри их системы оценки |
| Спекулятивная генерация | есть: черновики-модели + автоматическое распознавание встроенного MTP (признак в метаданных GGUF) | нет (поиск `speculative`/`nextn`/`MTP` по server/model/discover — пусто) |
| Эксперты MoE в оперативной памяти | есть: вынос экспертов, объём читается точно из списка тензоров GGUF | нет (поиск `override-tensor`/`exps` — пусто) |
| Сжатие KV-кэша | своя политика для каждой модели: q8_0 когда есть выигрыш, f16 когда сжимать нечего, q4_0 вручную | один на всех: переменная окружения `OLLAMA_KV_CACHE_TYPE`, умолчание f16 (`envconfig/config.go:222`) |
| Flash Attention | включён (CUDA-движок) | переменная `OLLAMA_FLASH_ATTENTION`, умолчание **выключен** (`envconfig/config.go:215-216`) |
| Раскладка карт | привязка модели к карте + перенос «целиком на другую карту» + явные пропорции разделения + вытеснение резидентов по расчёту; конфиг правится на лету | одна переменная `OLLAMA_SCHED_SPREAD` на всех, `main_gpu`/`num_gpu` в параметрах запроса; пропорций разделения нет; конфиг-файла нет — только переменные окружения и Modelfile |
| Версия llama.cpp | b11382 (beta10; живой сервер — b11429) | b11232 (снимок `42e911bc`) |

У Ollama также есть автоматика: появились ступени контекста по памяти —
на карте от 24 ГиБ значение 32k устанавливается автоматически. Оценка
помещаемости также реализована. Различие — в характере автоматики:
у Ollama она общая для всех моделей и статическая (ступени от суммарной
памяти, каждая загрузка рассчитывается с нуля); у llmhost — своя для
каждой модели и обучающаяся: профиль сохраняет фактический след именно
этой модели в этой форме запуска. Привязка к карте, разделение,
эксперты в оперативной памяти, спекуляция, MTP и конфигурация на лету
у Ollama либо отсутствуют, либо задаются сразу для всех моделей.

## Публичный замер: Qwen3-Next-80B с MTP на CUDA — автоматическая сборка пары (2026-10-07)

Насколько известно, это первый опубликованный замер MTP-головы для
Qwen3-Next на CUDA, в котором пару (основная модель и черновик)
собирает сам хостинг, а не ручные флаги. Сравнение с Ollama
неприменимо: спекулятивная генерация в Ollama отсутствует (см. таблицу
возможностей выше). Замер одиночный; база для сравнения — та же модель
без головы.

**Стенд:** карта RTX PRO 4000 Blackwell 24 ГиБ (единственная
задействованная; вторая, 3060, в замере не участвует), драйвер
580.178.04 (CUDA 13.0), движок llama.cpp **b11429** (сборка cuda12),
128 ГиБ оперативной памяти. Из 126 ГиБ занято 10 — 40 ГиБ экспертов
находятся в страничном кэше через отображение файла (вытесняемы,
в «занятой» памяти не считаются); на карте занято ~16,4 ГиБ.

**Модель:** Qwen3-Next-80B-A3B-Instruct, unsloth GGUF Q4_K_M, 45,2 ГиБ,
sha256 `f73551b55e3796526c37772c96227151fa11af328802b8f9865d635104e280fd`.
Черновик: a4lg/Qwen3-Next-80B-A3B-Instruct-MTP-ONLY-GGUF, Q8_0, 2,26 ГиБ,
sha256 `3200449f5387858ff9a6570728f409962fbac1443828fe01cea95653b2355729`
(файл сверен с LFS-oid до запуска). Пара собирается автоматически:
голова размещается как `MTP/mtp-*.gguf` рядом с основной моделью,
llmhost находит её и запускает процесс с `--model-draft`,
`--spec-type draft-mtp`, `--n-gpu-layers-draft 50` (слои самой головы +
выходной — черновик всегда на карте целиком, независимо от плана
основной модели).

**Конфигурация:** форма «эксперты в оперативной памяти» (`-ot exps=CPU`:
не-экспертные веса + KV-кэш + буферы на карте), все 48 слоёв и выходной
на карте, контекст 262144 (гибридная архитектура: токенный KV на
четверти слоёв + повторяющееся состояние), KV q8_0 + Flash Attention,
ubatch 2048.

**Замер** (сырой `/completion`, temperature 0, кэш промпта выключен,
уникальное окончание промпта на каждый прогон, счётчики движка):
генерация 512 токенов, 10 прогонов — **42,5 … 63,0 ток/с, медиана
48,9** (центральная пара 47,5/50,2); та же модель без головы —
35,3–35,7 (5 прогонов по 256) и 35,1–35,4 (4 прогона по 512 на том же
промпте). Итог: **×1,37** к базовой величине, худший прогон выше неё.
Прогрев: первый запрос после загрузки попадает на пик компиляции
графов и в медиану не входит.

Разброс присутствует: от 42,5 до 63,0 ток/с. Это не дефект разделения
по картам. Гипотеза из апстрим-issue #27428 («draft-mtp вызывает сбой
prefill при разделении слоёв») проверена на этой форме и отвергнута.
Длинное предзаполнение с головой — 889 ток/с, без головы — 906
(−1,9%). Счётчик повторного использования графов изменяется штатно:
127 проверочных графов на 512 токенов, примерно по 4 токена на граф.

Причина разброса — приём черновиков. Доля принятых подсказок на одной
и той же модели изменяется от 0,64 до 0,98. Вычисления MoE с экспертами
в оперативной памяти недетерминированы, и жадные продолжения расходятся
по веткам, которые черновик угадывает по-разному. Скорость со
спекуляцией растёт вместе с приёмом: около 30 ток/с при 0,66, около
45,5 при 0,966, около 59,5 при 0,979. Поэтому стабильные числа
получаются только на фиксированном промпте.

Неудачные траектории компенсирует сторож приёма: он самостоятельно
отключает черновик, если приём устойчиво низкий. С ним скорость
«хуже базовой величины» не сохраняется дольше двух минут.

Воспроизведение: разместить голову как `MTP/mtp-*.gguf` рядом с
основной моделью (или скачать через `lhctl pull`, если репозиторий
публикует пару); токены доступа не требуются — пара собирается при
`auto-draft: true` и `mtp-mode != off` (значения по умолчанию).

## Где llmhost уступает

- **Мелкие модели без MTP** — равенство с исполнителем Ollama на той
  же карте (496 против 496 на 0.6B): собственный форк ради ускорения
  декодирования не создаётся, а многослойная спекуляция на таких
  моделях невыгодна.
- **Первый токен (на прогретой системе)**: до ~35% быстрее прямой
  llama-server Ollama на части моделей (0,31 против 0,52 с на 26B в
  замерах того дня) — накладные расходы полного стека (прокси →
  роутер → процесс модели); на клиенте в локальной сети теряются в
  сетевом шуме.
- **Предзаполнение по матрице неровное**: на 12B длинное −6%, на 27B
  короткое −2% — в пределах разброса, кроме 26B длинное (+16% в
  пользу llmhost).

Преимущество — там, где работает автоматический MTP: +32% на 12B,
×1,8 на 27B, ×1,7 на 26B.

Карты разной скорости исключены из перечня уступок: «домашняя» карта —
самая быстрая, куда модель помещается целиком; если в момент загрузки
на ней мало свободной памяти, берётся следующая, где места хватает.
Ручной `main-gpu` сильнее. Вечерний прогон harness 9 октября без
ручной привязки разместил все четыре модели на Blackwell и повторил
утреннюю колонку: 513,9 / 74,4 / 53,9 / 197,7 ток/с.

## Методика (достоверность чисел)

- Одинаковые веса у обеих сторон (импорт через Modelfile `FROM`),
  сырое продолжение без шаблона чата, temperature 0, медиана трёх
  прогонов; ток/с — из собственных счётчиков движков (`timings` в
  llama.cpp против `eval_count/eval_duration` в Ollama).
- **Промпты должны быть уникальными, в том числе при генерации.**
  Повтор одного и того же текста искажает результат у обеих сторон.
  У Ollama 0.20.5 повторный идентичный сырой промпт не только
  «удешевляется»: ответ обрывается — `done:false` без `eval_count` и
  `eval_duration`. Это воспроизводится стабильно после первого целого
  прогона и похоже на дефект повторного использования KV-кэша на том
  стеке. У llmhost `cache_prompt: false` на повторном промпте
  сопровождается дорогостоящим сбросом слота кэша. Замер 1 октября:
  5 тысяч токенов на фиксированном промпте против фактических 11 тысяч
  на уникальном при том же объёме текста. Поэтому все прогоны
  выполняются на уникальных промптах. В обычной работе кэш
  переиспользуется у всех — проверено на практике: продолжение диалога
  обрабатывает только добавку.
- **Между фазами дожидаться фактического освобождения видеопамяти**
  (по nvidia-smi), а не выдерживать фиксированную паузу: однажды
  преждевременный старт привёл к незаметному вытеснению весов в общую
  память и падению скорости генерации в 7 раз без единой ошибки в
  журнале.
- `ollama serve` перед замером прогревается (свежезапущенный процесс
  даёт холодную первую загрузку ~29 с); после замера бенч-модель
  удаляется, сервер останавливается.

Повторение замера — по методике выше, подряд запросами к обоим API
(скрипт `scripts/bench_vs_ollama.py` остался от стенда предыдущего
поколения).
