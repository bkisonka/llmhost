# llmhost в Linux: руководство по командам

Практический справочник по работе с llmhost в Linux из терминала.
Установка, устройство системы и планировщик описаны в README; здесь
собраны команды повседневной работы.

---

## 1. Архитектура системы

Работают два вида процессов (оба выполняются от имени одного
пользователя):

```
llmhostd (демон)                        llama-server (движок, запускает демон)
 ├─ :7330  OpenAI-совместимый API       └─ по одному процессу на каждую модель,
 ├─ :7331  control API (к нему             находящуюся в видеопамяти
 │         подключается lhctl)
 └─ данные: ~/.local/share/llmhost
```

* **Порт 7330** — вход для клиентов в формате OpenAI:
  `/v1/chat/completions`, `/v1/completions`, `/v1/embeddings`,
  `/v1/models`. Через него работают библиотеки и приложения.
* **Порт 7331** — управление: статус, реестр, загрузка и выгрузка,
  скачивание, движок, замеры. `lhctl` является оболочкой над этим портом.
* Оба порта по умолчанию слушают **только 127.0.0.1**. Доступ извне
  организуется через SSH-туннель (см. раздел 9). Порт 7330 можно открыть
  в локальную сеть ключом `openai-bind = "0.0.0.0"` — тогда Bearer-ключ
  включается принудительно. Порт 7331 наружу не выставляется никогда.

**Движок и модель в памяти.** Движок — это программа llama-server из
llama.cpp. llmhost самостоятельно скачивает её, запускает и останавливает;
ручной запуск не требуется. Модель может находиться в двух состояниях.
Она **размещена в каталоге**: это файл на диске, количество таких моделей
не ограничено. Либо она **загружена в видеопамять**: веса находятся на
карте, модель отвечает на запросы. Для каждой загруженной модели работает
отдельный процесс llama-server. Выгрузка модели завершает его процесс и
освобождает память; лишних процессов не остаётся.

Режим работы демона — harness, выбирается не ключом, а устройством:
решения принимает демон — кому ждать памяти, кого выселять. Для каждой
модели в видеопамяти запускается отдельный процесс llama-server. Движок
можно обновлять, логика демона от этого не меняется.

Каталог данных (`app_dir`) определяется так: `$LH_DATA_DIR` →
`$XDG_DATA_HOME/llmhost` → `~/.local/share/llmhost`. В нём находятся
конфигурация, токен, журнал, движок и модели.

```
~/.local/share/llmhost/
├── llmhost.conf           единый конфиг: [general] — настройки (§6),
│                          остальные секции — тонкая настройка моделей (§7)
├── state.json             рабочее состояние: последняя модель, список
│                          моделей для восстановления после рестарта
│                          (пишется само; вручную править не нужно)
├── token.txt              Bearer-ключ API (права 0600)
├── model_profiles.json    самообучение планировщика: замеры следа моделей
│                          в видеопамяти (пишется сам после каждой загрузки)
├── log.txt                журнал (ротация 1 МиБ)
├── llmhostd.pid           pid-файл с блокировкой (один экземпляр на систему)
├── engine/                установленный llama.cpp (cuda12/vulkan)
└── models/                модели GGUF (можно переназначить models-dir)
```

Второй `llmhostd` одновременно не запускается (блокировка pid-файла):
второй экземпляр немедленно завершается с сообщением «уже запущен».

## 2. Запуск

### Установка из готового архива (без сборки)

```bash
curl -fsSL https://github.com/bkisonka/llmhost/releases/latest/download/install.sh | sh
```

Скрипт скачает статический архив с GitHub Releases, проверит контрольную
сумму SHA256, установит `llmhostd` и `lhctl` в `~/.local/lib/llmhost`
(символическая ссылка `lhctl` попадёт в `~/.local/bin` и в `PATH`),
поднимет службу systemd и установит движок (`cuda12` при NVIDIA, иначе
`vulkan`). Root не требуется, sudo не используется: все файлы размещаются
в домашнем каталоге (служба — systemd user unit, данные —
`~/.local/share/llmhost`). Бинарные файлы статические и не требуют
системных библиотек; из системных необходимы `curl`, `tar`, `sha256sum`.
Разработка и тестирование ведутся на Ubuntu — на других дистрибутивах
полноценная работоспособность не гарантируется (тестирование не
проводилось).

**Обновление** — повторный запуск той же команды (демон перезапускается,
данные и модели сохраняются); при нестандартном порте управления сначала
выполните `export LHCTL_PORT=ПОРТ`. Обновление движка выполняется всегда
отдельно: `lhctl engine update`. Флаги и переменные установщика —
`install.sh --help`.

### Сборка из исходников

```bash
cd ~/llmhost
cmake -S . -B build-linux && cmake --build build-linux -j$(nproc)
```

Результат: `build-linux/llmhostd` и `build-linux/lhctl`.

### Запуск на переднем плане (ознакомление и отладка)

```bash
LH_LOG_STDERR=1 ./build-linux/llmhostd     # журнал и в файл, и в консоль
./build-linux/lhctl status                 # из другого терминала
```

Остановка: Ctrl+C или `lhctl quit`. Демону достаточно сигнала SIGTERM —
он самостоятельно и корректно останавливает все процессы llama-server.

### Работа в качестве службы systemd (штатный способ)

```bash
scripts/install-systemd.sh          # юнит + enable --now
loginctl enable-linger              # поднимать при старте машины без входа
```

Управление и журнал:

```bash
systemctl --user status llmhostd
systemctl --user restart llmhostd   # после правки портов в llmhost.conf
journalctl --user -u llmhostd -f    # живой хвост журнала
```

Юнит настраивает `Restart=always` и `KillMode=control-group`: демон
всегда выполняется под управлением юнита — даже корректное завершение
(`lhctl quit`, SIGTERM) юнит считает аварией и поднимет демон через
2 секунды. Намеренная остановка выполняется только командой
`systemctl --user stop llmhostd`; после пересборки бинарного файла —
`systemctl --user restart llmhostd`. Запуск бинарного файла вручную
(setsid/nohup) не используйте — демон выйдет из-под управления юнита,
и служба-менеджер потеряет его из виду. Рестарт юнита завершает всё
дерево процессов (llama-server для каждой модели); осиротевших процессов
не остаётся. После принудительного завершения демона *вне* systemd
(`kill -9`) осиротевшие процессы удаляет следующий старт демона —
в журнале это строки с пометкой `orphan:`.

Чтобы `lhctl` был доступен из любого каталога:

```bash
mkdir -p ~/.local/bin && ln -s ~/llmhost/build-linux/lhctl ~/.local/bin/lhctl
```

### Первый запуск с нуля

```bash
TOKEN=$(cat ~/.local/share/llmhost/token.txt)
# 1) движок llama.cpp (один раз; 5–7 минут, проверяется SHA256):
curl -s -H "Authorization: Bearer $TOKEN" \
     -X POST 127.0.0.1:7331/v0/engine -d '{"build":"cuda12"}'
curl -s -H "Authorization: Bearer $TOKEN" 127.0.0.1:7331/v0/engine   # прогресс
# 2) модель (квант подберётся под ваши карты):
lhctl pull qwen3
# 3) разговор:
lhctl chat qwen3 "привет!"
```

## 3. lhctl: справочник команд

### Полноэкранный интерфейс

`lhctl` **без аргументов** открывает полноэкранный интерактивный
интерфейс: главный экран с реестром моделей и памятью карт, каталог
моделей (поиск → результаты → кванты с вердиктами
«влезает/частично/мимо» → скачать/загрузить), чат с моделью (лента
сообщений, Enter — отправить, Esc во время генерации — остановить,
`/clear`, `/bye`), управление токенами доступа к `/v1`. Данные
обновляются автоматически раз в секунду, изменение размера окна не
нарушает раскладку, выход возвращает терминал в исходное состояние
(демон продолжает работать).

```
↑↓, PgUp/PgDn     выбор модели
Enter, F3         карточка модели (C — ручной контекст модели)
F4                чат с выбранной моделью
F5                загрузить выбранную в видеопамять
F7                каталог моделей (поиск → кванты → скачать/загрузить)
F6                токены доступа к /v1 (создать/отозвать)
F8, u             выгрузить выбранную из видеопамяти
Ctrl-U            выгрузить все
F9, e             движок llama.cpp: зафиксированная версия, сборки, статусы;
                  F5 (или Enter) на экране — меню команд: обновить версию,
                  установить, переключить сборку; в шапке — установленный
                  и актуальный релиз с GitHub
Ctrl-D            удалить модель с диска, вместе со спутниками (спросит
                  подтверждение)
F10, q, Ctrl-C    выход
```

### Список команд

```
lhctl (без аргументов)          полноэкранный интерфейс. Если терминал ниже
                                35 строк, интерфейс просит у него
                                развернуться (XTWINOPS) и возвращает
                                исходный размер на выходе; терминал без
                                поддержки этой последовательности просто
                                игнорирует запрос — все экраны влезают в
                                любую высоту. Отключить: LH_TUI_NO_RESIZE=1
lhctl status [-w сек]           приборная панель: что в видеопамяти, полосы
                                памяти карт; -w — обновлять живьём
                                (Ctrl+C — выход)
lhctl models [--raw]            реестр моделей (--raw — идентификаторы
                                построчно)
lhctl show <модель>             карточка: архитектура, квант, слои, контекст
lhctl search <запрос>           поиск по каталогу Hugging Face: размер,
                                оценка памяти, влезет ли на ваши карты
                                (→ lhctl pull)
lhctl tokens [list]             именованные токены /v1: имя и значение
lhctl tokens add <имя>          выдать токен (пока они есть, /v1 отвечает
                                только по ним и общему ключу)
lhctl tokens rm <имя>           отозвать токен
lhctl chat [модель] [вопрос]    чат: диалог или один вопрос — один ответ
lhctl load <файл|имя>           загрузить модель в видеопамять (.gguf-путь
                                или имя из реестра)
lhctl pull [имя] [файл]         скачать модель с Hugging Face
lhctl pull stop                 остановить идущее скачивание (недокачанный
                                .part остаётся — повторный pull докачит)
lhctl engine                    движок: версия, активная сборка, установка
lhctl engine use <сборка|auto>  выбрать сборку для запуска (cuda12/vulkan;
                                auto — по железу)
lhctl engine update [сборка]    обновить llama.cpp: свежий релиз → версия →
                                установка
lhctl engine install <сборка>   (пере)установить сборку из текущей версии
lhctl ctx <модель> [N|auto]     ручной контекст модели: пишет ctx-size в
                                llmhost.conf
lhctl set [ключ [значение]]     настройки [general] llmhost.conf: без
                                аргументов — вся таблица; с аргументами —
                                записать и применить
lhctl unload [id]               выгрузить из видеопамяти одну (id) или все
                                (без аргумента); занятые модели не
                                выгружаются никогда — объяснение в ответе
lhctl rm <модель> [--yes]       удалить модель С ДИСКА (безвозвратно;
                                vision-проекция, MTP-модуль и части шарда —
                                вместе с ней)
lhctl quit                      завершить демон (модели выгружаются аккуратно)
lhctl version                   версия
lhctl completion bash|powershell  скрипт автодополнения
```

**Формат вывода.** В терминале команды выводят панели и таблицы
(рамки, цвет, авторазмер по ширине окна): `status` — приборная панель с
полосами памяти по картам, `models`/`search` — таблицы, `show`/`engine`
— карточки, скачивание (`pull`, `engine install`) — строка прогресса с
полосой, скоростью и оценкой времени; ширина окна перечитывается при
каждой отрисовке, поэтому изменение размера окна не нарушает
форматирование. В конвейерах и скриптах используется прежний машинный
вывод; `--json` (или `--raw` там, где он предусмотрен) возвращает его
принудительно и в терминале.

**Подключение.** Порт управления — 7331 (`--port N` или `LHCTL_PORT`).
Токен определяется автоматически: `--token XXX` → `LHCTL_TOKEN` →
`token.txt` из `~/.local/share/llmhost/` (та же установка, что у демона).
Для второй установки с `LH_DATA_DIR` задайте также
`LHCTL_PORT`/`LHCTL_TOKEN` — эти же переменные использует
автодополнение.

**Коды выхода** (для скриптов): `0` успех · `1` сервер недоступен ·
`2` неверный токен (401) · `3` ошибка запроса (404/500) · `4` ошибка
аргументов. Успешные ответы — в stdout, ошибки — только в stderr.

**Автодополнение** — команды и актуальные имена моделей по TAB:

```bash
echo 'source <(lhctl completion bash)' >> ~/.bashrc && source ~/.bashrc
lhctl load <TAB>     # подскажет модели из реестра (сервер выключен — молчит)
```

### status

```console
$ lhctl status
{
  "state": "loaded",
  "harness_mode": true,
  "models_max": 2,
  "busy": false,
  "queue_depth": 0,
  "pid": 12345,
  "version": "0.6.0-beta19",
  "models": [ { "id": "…", "state": "loaded", "embedding": false, "failed": false } ],
  "gpu":  { "name": "NVIDIA GeForce RTX 3060", "vram_free": …, "vram_total": … },
  "gpus": [ { "index": 0, "name": "…", "vram_free": …, "vram_total": … } ]
}
```

`state` — сводное состояние (`unloaded/loading/loaded`); `gpus` —
телеметрия карт (свободно и всего), на неё опирается планировщик. У
каждой модели в списке дополнительно видны `port` и `pid` её процесса
llama-server, поле `queue_depth` показывает, сколько запросов ожидает
в очереди пробуждения, `busy` — идёт ли генерация прямо сейчас.

### models

```console
$ lhctl models
Qwen3.8-27B-UD-Q4_K_XL  (в памяти)  [карта 0]
gemma-4-12b-it-UD-Q4_K_XL           [карта 1]
nomic-embed-text-v1.5-Q5_K_M  (в памяти)  [карта 0]
```

Пометка «в памяти» означает «загружена в видеопамять» (динамические
состояния: `в памяти`/`грузится…`/`не загрузилась`), `[карта N]` —
раскладка. `--raw` печатает только идентификаторы построчно (загруженные
первыми) — это те же строки, что идут в поле `model` API; формат для
скриптов и автодополнения. MTP-модули и vision-проекции в списке не
показываются, так как не являются самостоятельными моделями.

### show

```console
$ lhctl show Qwen3.8-27B-UD-Q4_K_XL
модель:      Qwen3.8-27B-UD-Q4_K_XL
файл:        /…/Qwen3.8-27B-UD-Q4_K_XL.gguf
размер:      17.5 ГБ
архитектура: qwen35, квант Q4_K_XL
слоёв:       64
контекст обучения: 262144 токенов
состояние:   loaded (карта 0)
```

Модель ищется по идентификатору, по `general.name` или по имени файла
без расширения (регистр не важен); во всех командах поиск выполняется
одинаково.

### ctx

Ручной контекст модели — то же, что ключ `ctx-size` в `llmhost.conf`,
но без ручного редактирования файла:

```bash
lhctl ctx qwen36              # показать: есть ли переопределение и каков план умной настройки
lhctl ctx qwen36 32768        # задать контекст 32768 токенов
lhctl mtp qwen36 off          # спекуляция модели: auto / on / off (детерминированно)
lhctl ctx qwen36 auto         # снять переопределение — снова решает умная настройка
```

Значение пишется в секцию модели `llmhost.conf` (секция создаётся,
существующее значение заменяется, комментарии и посторонние секции не
затрагиваются) и применяется сразу: модель выгружается из видеопамяти и
возвращается по первому запросу уже с новым контекстом; рестарт демона
не требуется. Разумный диапазон — 256…2097152 токенов. Переопределение
видно в карточке (`lhctl show`, строка «Ручной ctx») и в полноэкранном
интерфейсе (клавиша `C` в карточке модели). План умной настройки
показывается для сравнения: возможности карты и кванта не означают, что
следует выбирать большее значение.

### chat

Три формы:

```bash
lhctl chat                        # диалог с моделью по умолчанию
lhctl chat qwen3                  # диалог с конкретной (не в видеопамяти — загрузит)
lhctl chat qwen3 "вопрос одним предложением"   # один вопрос — один ответ
lhctl chat "вопрос"               # один аргумент с пробелом = вопрос
```

* Чат идёт через тот же OpenAI-порт :7330 — модель при необходимости
  загружается в видеопамять (прогресс точками, ожидание до 15 минут),
  диалог сохраняет контекст, ответы выводятся по мере генерации.
* «Размышления» думающих моделей (Qwen3 и подобные) отображаются
  приглушённым цветом. В режиме «один вопрос — один ответ» они скрыты —
  в stdout поступает только чистый ответ, что удобно для конвейеров:
  `lhctl chat qwen3 "столица Франции?" | wc -w`
* Команды диалога: `/bye` (или `/exit`, `/quit`, Ctrl+D) — выход,
  `/clear` — начать сессию заново.
* Модель по умолчанию («последняя используемая») — то же, что поле
  `model` без значения в API; буквально `lhctl chat any` также означает
  «по умолчанию».
* Векторная модель (эмбеддер) не может выступать собеседником — утилита
  предложит выбрать модель, поддерживающую диалог.

### load / unload

```bash
lhctl load qwen3                      # по имени из реестра
lhctl load /path/to/model-Q4_K_M.gguf # или по пути к файлу
lhctl unload qwen3                    # выгрузить одну из видеопамяти
lhctl unload                          # выгрузить все
```

`load` идемпотентен: «уже загружена» — не ошибка. Если модели вместе
не помещаются в видеопамяти, планировщик самостоятельно вытеснит
наименее востребованную и дождётся освобождения памяти. Команда
возвращается сразу, прогресс — в `lhctl status`/`lhctl models`.

**Правило занятости:** модель, которая в данный момент отвечает на
запрос, не выгружается. `lhctl unload` для такой модели откажет и
объяснит причину; `lhctl unload <модель> --force` снимет её
принудительно, оборвав все генерации модели для её клиентов.
`lhctl unload` без аргумента выгрузит все свободные модели и
перечислит занятые; их впоследствии выгрузит сторож простоя. Если
запрос столкнулся с занятыми моделями, он ожидает в очереди
(`queue-ttl` секунд) и выполняется, как только память освободится.

### pull

```bash
lhctl pull                 # список коротких имён (живой, с сервера)
lhctl pull qwen3           # квант выберется под вашу карту (+MTP и vision-проекция, если есть)
lhctl pull qwen3-0.6b      # мелкая — как черновик для спекуляции
lhctl pull embed           # векторная модель для поиска по документам
lhctl pull org/Repo-GGUF   # любой репозиторий целиком
lhctl pull org/Repo-GGUF "*Q4_K_M*"   # с фильтром файлов (маска)
lhctl pull stop            # остановить идущее скачивание
```

Ход загрузки отображается строкой с процентами и скоростью. Пока
загружается одна модель, `pull` другой вернёт 409 и **присоединится к
текущей загрузке** (это не ошибка). Остановить идущую загрузку можно
`lhctl pull stop` (или `Ctrl-X` в полноэкранном интерфейсе): загрузка
прерывается, недокачанный `.part` остаётся на диске, повторный `pull`
продолжает с места останова. Загруженное сразу попадает в реестр
— `lhctl models` отобразит его. Поддерживается набор коротких имён
(`qwen3`, `qwen3-30b`, `gemma-4`, `llama`, `ministral`, `granite`,
`phi`, `embed`, …), полный список — `lhctl pull` без аргументов.

### engine

Движок устанавливается готовыми сборками llama.cpp; зафиксированная
версия (тег релиза, адрес, контрольная сумма SHA256) хранится в
`manifest.json` рядом с демоном. Команда `engine` охватывает весь цикл —
просмотр, обновление, установку и откат:

```bash
lhctl engine                          # версия, активная сборка, что установлено
lhctl engine update                   # свежий релиз llama.cpp: версия + установка активной сборки
lhctl engine update --pin-only        # только переписать манифест (установка — позже)
lhctl engine update --release b11379  # конкретный релиз вместо последнего
lhctl engine update --all             # все зафиксированные сборки (cuda12 + vulkan)
lhctl engine install vulkan           # (пере)установить сборку из текущей версии
lhctl engine use cuda12               # запускать именно эту сборку (модели перезапустятся)
lhctl engine use auto                 # снять выбор — снова по железу (NVIDIA → CUDA)
```

Как работает `update`: через GitHub API находится свежий релиз-тег
`bNNNNN`, из его файлов берутся контрольные суммы и размеры —
`manifest.json` переписывается атомарно (прежний сохраняется в
`manifest.json.bak`), затем выбранная сборка устанавливается с
отображением прогресса и проверкой SHA256. Сами архивы при смене версии
не скачиваются. «latest» — самый свежий тег вида `bNNNNN`: версионные
релизы `v*` публикуются выше как указатели без бинарников, и они
игнорируются.

- **Откат**: `lhctl engine update --pin-only --release <старый тег>`
  или вернуть `manifest.json.bak` на место и переустановить.
- **Версия и установка раздельны**: смена зафиксированной версии не
  затрагивает бинарные файлы — её можно выполнять при загруженных
  моделях; установке требуется свободный демон (модели выгружены из
  видеопамяти), иначе `409`. Установка сама останавливает работающие
  модели — следующая загрузка будет выполнена уже на новом движке.
- **Выбор сборки** (`engine use`): по умолчанию сборка выбирается по
  железу (NVIDIA → первая CUDA-сборка манифеста, иначе Vulkan). Явный
  выбор записывается в llmhost.conf (`engine-build`) и сохраняется через
  рестарты; применяется сразу — модели перезагрузятся по первому
  запросу. Сборка должна
  быть зафиксирована и установлена. В `lhctl status` движок показывается
  как есть («Движок: cuda12 …»); галочка «Vulkan ✓» в строке «Железо»
  означает лишь наличие Vulkan-загрузчика в системе и на выборе сборки
  не сказывается.
- Если в релизах llama.cpp изменилась схема имён архивов — смена версии
  откажет, назвав ненайденный файл; тогда `manifest.json` правится
  вручную.
- Автоматическая проверка обновлений отсутствует — обновление
  выполняется только явной командой.
- **Профили планировщика привязаны к релизу движка**: установка
  **другого** релиза сама сбрасывает замеры следа в видеопамяти
  (повторный замер при следующих загрузках; в журнале — «замеров
  сброшено N»). Переустановка того же релиза и откат версии без
  установки замеры сохраняют. При ручной замене бинарных файлов удалите
  `~/.local/share/llmhost/model_profiles.json` вручную.

### Спекуляция с MTP-модулем (автоматический режим)

Модели с родным MTP-модулем (черновик, обученный вместе с моделью)
ускоряются без настройки — так же, как vision-проекции: модуль,
расположенный рядом с моделью (подпапка `MTP/` репозитория),
подключается автоматически, и в журнале появляется
`speculative decoding (авто)`. Если модуля нет, модель работает без
спекуляции. `lhctl pull` по короткому имени скачивает модуль вместе с
моделью, если он есть в каталоге.

- Отключить для всех моделей: `mtp-mode = off` в `[general]`
  llmhost.conf.
- Включить вручную для конкретной модели (например, модуль расположен
  в другом месте): секция в llmhost.conf — `model-draft = <файл>` и
  `spec-type = draft-mtp`.
- Если черновику не хватило места, загрузка автоматически повторится
  без спекуляции; клиент ошибки не получит.
- Эффект измеряется полем `timings` в ответе `/completion` или
  сравнением `lhctl chat` до и после.

### rm

```bash
lhctl rm qwen3-0.6b         # спросит подтверждение (y/N)
lhctl rm qwen3-0.6b --yes   # без вопроса — для скриптов
```

Удаление безвозвратное. Корзина не предусмотрена. Вместе с моделью
удаляются файлы, скачанные вместе с ней: vision-проекция, MTP-модуль
(в том числе из подпапки `MTP/` репозитория) и остальные части группы
`…-00001-of-00003.gguf`, а также недокачанные `.part` этих файлов.
Подтверждение показывает список спутников и общий размер. Модуль,
который требуется другой используемой модели в той же папке (второй
квант того же репозитория), остаётся. Пустые папки репозитория
удаляются. Модель, находящаяся в данный момент в видеопамяти, при
удалении выгружается автоматически. В неинтерактивном вводе (конвейер
или скрипт) без `--yes` команда откажет в выполнении и ничего не
удалит.

### quit

Аккуратно останавливает демон: все процессы llama-server завершаются,
видеопамять освобождается; список загруженных моделей
сохраняется и после рестарта демона восстанавливается автоматически.
Под systemd предпочтительнее `systemctl --user stop llmhostd` — эффект
тот же.

## 4. Control API (:7331): справочник curl

Все функции `lhctl` доступны и напрямую — авторизация обязательна:

```bash
TOKEN=$(cat ~/.local/share/llmhost/token.txt)
H="Authorization: Bearer $TOKEN"
BASE=127.0.0.1:7331
```

| Метод и путь          | Что делает |
|-----------------------|------------|
| `GET  /v0/status`     | сводное состояние, данные карт; по процессу на модель (порт, pid) и глубина очереди |
| `GET  /v0/metrics`    | текст Prometheus: счётчики прокси, токены, память карт, состояния + точная телеметрия движков по-модельно (`llmhost_engine_*`: скорости декода и префилла, приём спекции, токены — из `/metrics` живых детей) |
| `GET  /v0/hardware`   | только телеметрия карт |
| `GET  /v0/models`     | реестр: архитектура/квант/размер/слои + живое состояние, карта, «светофор» (поместится ли, максимальный контекст) |
| `POST /v0/load`       | `{"path": "…"}` или `{"name": "…"}` → `202` (прогресс опросом /v0/models) |
| `POST /v0/unload`     | `{}` — выгрузить всех незанятых; `{"model": "<id>"}` — одну (занятая → 409, неизвестный id → 404); `{"model": "<id>", "force": true}` — занятую принудительно (обрывает все генерации модели) |
| `DELETE /v0/models`   | `{"path": …}` или `{"name": …}` — удалить файл (безвозвратно) |
| `GET  /v0/pull`       | статус закачки (state/file/done/total/speed) |
| `POST /v0/pull`       | `{"repo": "org/repo", "file": "фильтр?"}` → `202` |
| `GET  /v0/aliases`    | короткие имена для pull |
| `GET  /v0/catalog/search?q=qwen&limit=24` | поиск по Hugging Face |
| `GET  /v0/catalog/model?repo=org/repo` | карточка репозитория + светофор |
| `GET  /v0/engine`     | сборки из manifest.json (release, active) и статус установки |
| `POST /v0/engine`     | `{"build": "cuda12"}` — скачать/установить (409, если модели в видеопамяти) |
| `POST /v0/engine/pin` | `{"release": "latest"\|"bNNNNN"}` — переписать зафиксированную версию (SHA256 из GitHub API; 502 — нет файла) |
| `GET  /v0/bench`      | результат замера сборок (winner/winner_tps/results) |
| `POST /v0/bench`      | `{"path": "модель.gguf"}` или `{}` (модель подберётся сама) → `202` |
| `GET  /v0/credentials`| OpenAI-адрес и ключ для клиентов |
| `POST /v0/quit`       | аккуратное завершение демона |

Ошибки возвращаются в стабильной форме `{"error":{"message","type","code"}}`.
Примеры (`jq` в комплект сервера не входит — форматированная печать
выполняется одной строкой python3):

```bash
# что в видеопамяти и сколько памяти свободно на картах
curl -s -H "$H" $BASE/v0/status | python3 -c "import json,sys; d=json.load(sys.stdin); \
  print(d['state']); [print(g['index'], g['name'], g['vram_free']>>20, 'МиБ свободно') for g in d['gpus']]"

# сводка реестра: id, состояние, карта, светофор
curl -s -H "$H" $BASE/v0/models | python3 -c "import json,sys; \
  [print(m.get('id',m['name']), m.get('state',''), m.get('gpu',''), m.get('fit',{}).get('fits')) \
   for m in json.load(sys.stdin)['models']]"

# загрузить и следить:
curl -s -H "$H" -X POST $BASE/v0/load -d '{"name":"qwen3"}'
watch -n1 "curl -s -H '$H' $BASE/v0/models | python3 -c \"import json,sys; \
  [print(m.get('id',m['name']), m.get('state','')) for m in json.load(sys.stdin)['models']]\""

# замер движков (vulkan против cuda), потом победитель:
curl -s -H "$H" -X POST $BASE/v0/bench -d '{}'
curl -s -H "$H" $BASE/v0/bench
```

## 5. OpenAI-совместимый API (:7330)

```bash
KEY=$(cat ~/.local/share/llmhost/token.txt)   # ключ тот же (см. /v0/credentials)
curl -s 127.0.0.1:7330/v1/chat/completions \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{
        "model": "Qwen3.8-27B-UD-Q4_K_XL",
        "messages": [{"role":"user","content":"привет!"}],
        "stream": true
      }'
```

* **model** — идентификатор из `lhctl models --raw`. Если поле пустое,
  равно `"any"` или не указано, подставится модель по умолчанию
  (последняя использованная; единственная разговорная в реестре; первая
  загруженная). Если кандидатов нет — 400 с подсказкой.
  Неизвестное имя: если модель есть в реестре — она загрузится в
  видеопамять; при неудаче возвращается ошибка с объяснением.
* Модели, которых нет в видеопамяти, **загружаются автоматически** при
  первом запросе (с вытеснением незанятых, если нужна память) — первый
  ответ приходит с большей задержкой. Сторож простоя впоследствии
  выгрузит её по истечении `unload-after-min` минут бездействия.
* Поддерживается весь функционал llama-server: потоковая выдача
  (`stream`), `/v1/completions`, `/v1/embeddings` (векторная модель:
  `lhctl pull embed`), `/v1/models`. Vision-модели принимают картинки
  стандартным видом OpenAI
  (`content: [{type:"image_url", image_url:{url:"data:image/png;base64,…"}}]`),
  если у модели есть vision-проекция или MTP-модуль, pull докачает
  подходящий файл автоматически.
* Думающие модели: отключить размышления можно на клиенте —
  `"chat_template_kwargs": {"enable_thinking": false}` (размышления в
  ответе идут полем `reasoning_content`).
* Авторизация: если `openai-auth: true` (умолчание) — Bearer-ключ
  обязателен. При внешней привязке (`openai-bind` не localhost) проверка
  включается принудительно, отключить её нельзя. На localhost
  `openai-auth: false` снимает проверку (сервер не слушает внешние
  интерфейсы, пока это не задано явно).
* Лимит тела запроса — 256 МиБ (длинные промпты и вложения).

### Клиенты (Python и другие)

```python
from openai import OpenAI
client = OpenAI(base_url="http://127.0.0.1:7330/v1",
                api_key=open("/home/you/.local/share/llmhost/token.txt").read().strip())
r = client.chat.completions.create(
    model="Qwen3.8-27B-UD-Q4_K_XL",   # или "any"
    messages=[{"role": "user", "content": "привет!"}],
    stream=True,
)
for chunk in r:
    print(chunk.choices[0].delta.content or "", end="", flush=True)
```

Любая библиотека или приложение с полем OpenAI base URL настраивается
так же: `http://127.0.0.1:7330/v1` + ключ из token.txt.

## 6. Настройка: llmhost.conf (секция [general])

`~/.local/share/llmhost/llmhost.conf` — единый конфигурационный файл
приложения (INI-формат): `[general]` — глобальные настройки, остальные
секции — тонкая настройка моделей (§7). Правится вручную или через
`lhctl set`; записывают сюда и команды демона (`lhctl ctx`,
`lhctl engine use/update`), а также установщик.

Применение: большинство ключей действует **на лету** (наблюдатель за
файлом применяет правку за секунды); порты, `openai-bind`, `openai-auth`
и `cors-origins` при работающем демоне не
меняются — после их правки выполните `systemctl --user restart llmhostd`
(демон сам сообщит об этом в журнале).

```
[general]
ctx = 4096
models-dir = /data/models
```

Ключи `[general]` (та же таблица через `lhctl set`; API — GET/POST
/v0/settings):

| Ключ | Умолчание | Смысл |
|------|-----------|-------|
| `openai-port` | 7330 | порт OpenAI-прокси (нужен рестарт демона) |
| `control-port` | 7331 | порт управления (и порт lhctl) (нужен рестарт) |
| `openai-bind` | "127.0.0.1" | адрес привязки OpenAI-порта: `"0.0.0.0"` — служба в локальной сети. При не-localhost привязке Bearer-ключ включается принудительно (нужен рестарт) |
| `openai-auth` | true | требовать Bearer-ключ на :7330 (нужен рестарт) |
| `cors-origins` | — | дополнительные доверенные источники для CORS через запятую (localhost разрешён всегда) (нужен рестарт) |
| `queue-ttl` | 120 | сколько секунд запрос согласен ждать в очереди пробуждения; 0 — ждать нельзя, занято → сразу отказ |
| `queue-depth` | 16 | сколько запросов максимум может ждать одну модель |
| `slot-park` | true | парковка KV-состояния слотов на NVMe — при выселении простойной модели сторож сохраняет KV слотов в `<data>/slot_parks/`, при пробуждении возвращает, и ход клиента попадает в кэш промпта вместо полного перепрефилла (возврат ~2 с против 12–20+ с на больших контекстах, замер 30.10). Отказы best-effort: не сохранилось/не восстановилось — слот просто холодный |
| `slot-park-min-tokens` | 8192 | глубина промпта слота, ниже которой парковка не делается (возврат с диска дороже перепрефилла); 0 — паркуем любые тронутые слоты |
| `slot-park-gib` | 64 | потолок суммарного размера файлов парковки; превышен — новое сохранение пропускается с записью в журнале; 0 — без предела |
| `moe-cpu-share` | 0 | доля промахов кэша MoE, которую движок считает на CPU параллельно с GPU (PR #30966, `--moe-cache-cpu-share`); сетка учитывает её в модели промахов, планировщик передаёт флаг только вместе с выданным грантом. Кривая по share — перевёрнутый U (замер 31.10 на 8-ядерном Ryzen, Flash-Next @65k): 0 → 29,5, 0.3–0.4 → ~40, **0.5 → 42,4 (оптимум)**, 0.7 → 37,1; при share > 0 помогает и `-t` = физическим ядрам |
| `models-max` | 2 | сколько моделей демон держит в видеопамяти (0 — без лимита; лишнее выгрузится по давности) |
| `parallel` | 1 | одновременных потоков запросов на модель (суммарный контекст делится между ними, минимум 2048 на поток; меньший контекст режет число потоков) |
| `moe-cache-mib` | 0 | кэш горячих MoE-экспертов в видеопамяти: `-1` — авто (план сравнивает раскладки по прогнозу резидентности и выбирает сам), `0` — выключить, `N` — вручную (МиБ на карту; бюджет карты режет физику). Замеры 28–29.10: 30B-A3B ×2,9 (37% пула), Next-80B ×1,9 (27%); малые доли больших пулов снижают скорость (трэш кэша — предупреждение в журнале) |
| `auto-params` | true | умный подбор: контекст «сколько влезет», сжатый KV-кэш, раскладка по картам. false — брать `ctx`/`ngl` как есть |
| `ctx` | 4096 | контекст по умолчанию (основа при `auto-params: false`; минимум — 256) |
| `ngl` | 999 | слоёв на видеокарту (999 — все) |
| `ubatch` | 0 | физический размер пачки у llama-server; 0 — умолчание движка (512) |
| `threads` | 0 | CPU-потоки ребёнка (`-t`); 0 — умолчание движка (hardware_concurrency = SMT). Замер 31.10: на exps_cpu-формах с `moe-cpu-share > 0` физические ядра бьют SMT (Ryzen 5700X: 8 → +3 ток/с) |
| `unload-after-min` | 15 | минуты бездействия до выгрузки из видеопамяти; 0 — никогда |
| `gpu-pin` | true | сажать модель на самую быструю карту, куда она влезает целиком; если в момент загрузки там мало свободной памяти — на следующую |
| `auto-draft` | true | спекулятивная генерация: MTP-модуль или младшая модель семейства автоматически |
| `mtp-mode` | "auto" | MTP-модуль: `auto\|on\|off` |
| `models-dir` | `<данные>/models` | каталог с моделями GGUF (установщик спрашивает и пишет сюда) |
| `engine-build` | — | сборка движка (`cuda12`/`vulkan`); пусто — по железу |
| `lang` | auto | язык интерфейса: `auto` — по локали машины (русская → русский, любая другая → английский), `ru`/`en` — форс; применяется живьём (lhctl/TUI и клиентские ответы демона), без рестарта |
| `engine-release` | — | зафиксированный релиз движка (`b11541`); пусто — затравка из manifest.json. `lhctl engine update` пишет сюда после проверки всего конфига — покорёженный файл версию не получит |
| `llama-server` | — | путь к llama-server; пусто — из установленного движка |

Пер-модельные переопределения (секция модели в llmhost.conf): `ctx-size`,
`moe-cache-mib` — размер кэша MoE этой модели в МиБ (0 — решает `[general]`;
оптимум у моделей разный: Flash-Next 8192, Next-80B 10752 — замер 30.10),
`n-gpu-layers`, `main-gpu`, `tensor-split`, `model-draft`, `spec-type`,
`cache-type`, `system`, `mtp-mode`, `vision-mode`, `thinking-mode`
(thinking ребёнка: auto — решает движок по шаблону, on/off — форс
`--reasoning`; `lhctl thinking <модель> [auto|on|off]`, клавиша T карточки),
`draft-card`,
`expert-card`. API: `POST /v0/models/ctx` (ручной контекст),
`POST /v0/models/cache` (пер-модельный кэш, 0 — снять override),
`POST /v0/models/mtp`, `POST /v0/models/vision`,
`POST /v0/models/thinking`.

Рабочее состояние (`last_model` — последняя модель для
автовосстановления, `resident` — список моделей в видеопамяти для
восстановления после рестарта, `mtp_choices` — ответы
про MTP-модуль) хранится отдельно в `state.json` — в конфигурационный
файл оно не входит. Установки со старым `config.json` переносятся
автоматически при первом старте нового демона: значения — в
`[general]`, файл переименовывается в `config.json.migrated`.

## 7. Секции моделей в том же llmhost.conf

Тот же файл, что и настройки (§6): глобальные — в `[general]`, тонкая
настройка моделей — отдельной секцией на модель. Заголовок секции —
идентификатор модели (имя файла без `.gguf`). **Перечитывается на лету**
(наблюдатель за файлом) — рестарт не требуется. Переопределения имеют
приоритет над умной настройкой:

```ini
[Qwen3.8-27B-UD-Q4_K_XL]
main-gpu = 1
cache-type = q8_0
ctx-size = 65536
system = Ты — дежурный ассистент. Отвечай кратко.

[gemma-4-26B-A4B-it-UD-Q4_K_M]
tensor-split = 0,1
```

Комментарии — строка целиком, начинающаяся с `#` или `;`. Старый формат
`model_overrides.json` читается, только если `llmhost.conf` отсутствует
(переезд без правки старых установок — достаточно создать conf и
перенести нужное).

| Ключ | Смысл |
|------|-------|
| `ctx-size` | общий контекст модели (делится между потоками `parallel`) |
| `n-gpu-layers` | сколько слоёв на видеокарте (0 — как рассчитал планировщик) |
| `main-gpu` | привязка к карте (0, 1, …); не задано — автоматический выбор |
| `tensor-split` | пропорции разделения по картам, например `0,1` — всё на карту 1. Явно заданное человеком исполняется как написано |
| `cache-type` | тип KV-кэша: `f16` (максимальное качество) / `q8_0` / `q4_0` (сжатие; q4 в расчётах считается как q8) |
| `system` | системный промпт: подкладывается клиентам, не приславшим свой |
| `model-draft` | черновик для спекулятивной генерации (идентификатор/имя/путь) |
| `spec-type` | `draft-simple` (умолчание), `draft-mtp`, `eagle3`, `ngram-*` |

`main-gpu` — предпочтение. Планировщик действует по ступеням: сначала
указанная карта целиком, затем другая карта целиком, затем разделение
по всем картам, затем часть слоёв в оперативной памяти. Если на
указанной карте модель целиком не помещается, а на другой помещается,
она будет размещена там. В журнале появится строка «пин карты N не
вмещает — целиком на карту M». Без переопределений модель размещается
на самой быстрой карте, куда помещается целиком. Если в момент загрузки
там мало свободной памяти, берётся следующая. Встроенный MTP
(Qwen3.6/3.5, GLM-4.5 и подобные) включается без ключей: признак
читается из GGUF, спекуляция выполняется в режиме `draft-mtp` без
отдельного файла.

**Самообучение планировщика.** Расчёт памяти по формулам приближённый,
погрешность — порядка гигабайта: рабочие области MoE, гибридные
архитектуры, NVFP4. Демон обучается на фактических загрузках. После
каждой успешной загрузки он измеряет фактический след в видеопамяти и
записывает надбавку сверх весов и KV-кэша в `model_profiles.json`.
Профиль относится к своей форме запуска: выходной слой на карте или в
оперативной памяти, тип кэша, ubatch, класс движка, эксперты в
оперативной памяти, число слоёв при частичной загрузке. На другой
контекст профиль масштабируется. Следующая загрузка планируется уже по
нему.

Форм у модели несколько, у каждой свой профиль. Загрузка «эксперты в
оперативной памяти» не перезапишет замер полной формы, и наоборот. Если
при малом запасе расчёт отказывает выходному слою, демон пробует
включить его в ходе загрузки. При нехватке памяти модель перезагружается
без него (без сообщения об ошибке) и запоминает неудачу. В журнале это
строки `profiles:`. Файл можно удалить — планировщик начнёт обучение
заново.

## 8. Диагностика

```bash
journalctl --user -u llmhostd -f          # живой журнал (под юнитом)
tail -f ~/.local/share/llmhost/log.txt    # тот же журнал файлом (≤1 МиБ)
lhctl status                              # жив ли и что в видеопамяти
nvidia-smi                                # память карт: сходится с lhctl status
```

* **Ошибка 401** в ответах — токен не совпал: сверьте `--token`/
  `LHCTL_TOKEN` с `token.txt` той установки, куда смотрит `LH_DATA_DIR`.
* **503 «Bearer-токен не создался»** — генератор случайных чисел
  недоступен; API намеренно закрыт (безопасность важнее удобства), а не
  открыт для всех.
* Упавший запрос к движку (статус ≥400) сохраняет диагностические
  данные рядом с журналом: `failed_request.json` (тело запроса — можно
  повторить curl'ом) и `failed_server_tail.txt` (хвост вывода llama-server,
  там причина — например, `failed to allocate CUDA… buffer`).
* **«порт занят»** в журнале — порты 7330/7331 уже заняты другим
  процессом: контейнерный стек или второй экземпляр. Порты можно сменить
  в llmhost.conf (openai-port/control-port) — затем рестарт юнита.
* Самопроверка API: `python3 tests/api_e2e.py --quick` (без генераций;
  токен и порты определяются из каталога данных автоматически). Полный
  прогон с генерациями — тот же скрипт без `--quick`.
  Многопользовательский сценарий —
  `tests/harness_multiuser_e2e.py`.
* Осиротевшие после `kill -9` демона процессы llama-server удаляются
  при следующем старте (строки `orphan:`) — память карт освобождается
  автоматически.
* Журнал отражает работу очереди пробуждения: строки
  «паркуется: ждёт освобождения занятых» — запрос поставлен в очередь,
  «выселяю незанятого резидента» — демон освободил память для нового,
  «истекло ожидание» — запрос не дождался и получил 504.

## 9. Типовые сценарии

**Внешняя служба в локальной сети** — два ключа в `[general]`
llmhost.conf и рестарт юнита:

```ini
[general]
openai-port = 5050
openai-bind = 0.0.0.0
```

```bash
systemctl --user restart llmhostd
# проверка с любого хоста сети (Bearer-ключ обязателен — при внешней
# привязке он включается принудительно):
curl -s http://192.168.1.150:5050/v1/models -H "Authorization: Bearer <ключ>"
```

Порт управления (:7331) при этом остаётся доступным только на localhost
— управление наружу не выставляется никогда. Порт 5050 должен быть
свободен: если на сервере ещё работает старый стек (docker-контейнер),
его следует остановить (`docker compose down` в его каталоге), иначе
демон не займёт порт.

**Доступ с ноутбука без открытия порта в сеть** (умолчание
`openai-bind = "127.0.0.1"` — наружу через туннель):

```bash
ssh -L 5050:127.0.0.1:5050 -L 7331:127.0.0.1:7331 user@server
# на ноутбуке: base_url http://127.0.0.1:5050/v1, ключ с сервера
```

**Две модели в видеопамяти** (диалог + векторная для поиска по
документам):

```bash
lhctl pull qwen3 && lhctl pull embed
lhctl load qwen3 && lhctl load embed
# обе в видеопамяти (models-max: 2), прокси сам адресует запросы:
#   чат → "model": id разговорной модели, векторы → id векторной
```

**Несколько пользователей на одном сервере.** Откройте службу в
локальную сеть (см. «Внешняя служба в локальной сети» выше) и
предоставьте всем один адрес. Занятая модель во время чужого ответа не
выгружается. Запрос, которому не хватило памяти, ожидает в очереди и
выполняется, когда память освободится.

**Фоновая задача с гарантией кода выхода:**

```bash
lhctl chat qwen3 "составь план на день" || echo "провал: код $?" >&2
```

**Проверка перед завершением работы** (что останется в видеопамяти):

```bash
lhctl models                 # пометка (в памяти) — кто загружен
lhctl unload                 # освободить всё незанятое
```

**Собственная раскладка по картам.** Пример: разместить большую
MoE-модель целиком на карте 1 — жёстче автоматического выбора:

```ini
[Qwen3-30B-A3B-Q4_K_M]
main-gpu = 1
tensor-split = 0,1
```

(записывается в llmhost.conf, применяется при следующей загрузке
модели).

**Пересчитать контекст или тип кэша** для одной модели:

```ini
[Qwen3.8-27B-UD-Q4_K_XL]
ctx-size = 131072
cache-type = f16
```

Если с f16 не помещается — демон сообщит об этом в журнале и
останется на сжатом кэше.

**Обновление демона** (юнит указывает на бинарный файл — достаточно
пересобрать):

```bash
cd ~/llmhost && git pull && cmake --build build-linux -j$(nproc)
systemctl --user restart llmhostd
```
